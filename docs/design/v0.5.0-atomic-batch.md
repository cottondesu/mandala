# v0.5.0 — Atomic Batch Operations + Dry-run Design

Status: frozen before implementation. Baseline: v0.4.1 (`bdff5992e2935d1a55919ec58e111cdaa824f7fc`).

## 1. Goals

1. `mandala batch` applies a JSON-described list of `add`/`mark` operations atomically: all operations succeed and are saved exactly once, or nothing is saved.
2. `--dry-run` executes the identical validation and apply pipeline against a working copy and reports the deterministic preview without touching state.
3. Preview is a deterministic, ID-sorted semantic diff of cells (not an operation log), renderable as compact JSON or fixed text.
4. Input comes from a JSON file or stdin (`--file -`) under strict parsing rules: known keys only, no duplicate keys, no null, exact types, bounded size and operation count.

## 2. Non-goals

- No `init`, `clean`, `remove`, `rename`, `move`, import/export in batch.
- No multi-state updates; one project per run.
- No AI cell generation.
- No multi-process locking, no CAS / state-hash precondition (reserved for a future version).
- No SQLite, no network, no new dependencies (standard library only).
- No expansion of atomicity beyond a single CLI run: no filesystem-failure rollback, no power-loss durability, no exactly-once, no lost-update prevention (single-writer model retained).

## 3. User-facing CLI contract

```sh
mandala batch --file operations.json            # apply; stdout empty
mandala batch --file operations.json --dry-run  # text preview; no save
mandala batch --file operations.json --dry-run --json  # JSON preview
mandala batch --file - --dry-run --json         # stdin input
mandala batch --file operations.json --json     # apply + JSON result (after save)
mandala --project DIR batch --file operations.json --dry-run --json
```

Flags (command-local, after `batch`, before/no positional arguments):

| Flag | Type | Behavior |
|---|---|---|
| `--file` | string | Required. Path to JSON input, or `-` for stdin. Relative paths resolve against the process working directory, never against `--project`. |
| `--dry-run` | bool | Default false. Validate + apply on a working copy, never save. |
| `--json` | bool | Default false. Compact one-line JSON result plus one LF. |

- Omitted `--file`, empty `--file` value, or `--file` specified more than once: `E_USAGE`, exit 2.
- Unknown flags and extra positional arguments: `E_USAGE`, exit 2.
- `batch --help` follows the existing per-command help convention (usage line, exit 0).
- Batch operates only on an existing project; it never implicitly runs `init`.

Output matrix:

| Run | stdout | Exit |
|---|---|---|
| Apply (no `--json`) | empty | 0 |
| Apply + `--json` | JSON result (`dry_run:false`) | 0 |
| Dry-run | text preview | 0 |
| Dry-run + `--json` | JSON preview (`dry_run:true`) | 0 |
| Any validation/application error | empty | 2 |

Batch never exits 1, even when required gaps remain after a successful apply.

## 4. JSON input schema (batch input v1)

```json
{
  "batch_version": 1,
  "operations": [
    {"op": "add", "id": "security"},
    {"op": "add", "id": "security.csrf"},
    {"op": "add", "id": "tests", "optional": true},
    {"op": "mark", "id": "security.csrf", "status": "done"}
  ]
}
```

Root object: exactly the keys `batch_version` (JSON integer literal `1` only — `1.0`, `1e0`, `"1"`, `null` rejected) and `operations` (array). Each key exactly once. Unknown keys rejected. No null anywhere.

- `add` object: allowed keys `op`, `id` (required), `optional` (optional, JSON boolean, default false). Any other key (including `status`) rejected.
- `mark` object: allowed keys `op`, `id`, `status`, all required. `status` ∈ {`open`,`done`,`na`} as a JSON string; `expanded` is rejected; `optional` is rejected even when false.

All existing domain rules apply unchanged and are enforced by the existing mutators: ASCII ID grammar, two-level depth, ≤8 roots, ≤8 children per root, ≤72 cells, parent existence before children, optional inheritance, no marking an expanded parent, no adding children under `done`/`na` parents, no duplicate IDs (including within one batch).

Limits: input ≤ 65,536 bytes (measured by bytes actually read, not file metadata; reads are bounded so oversized streams never stream unbounded), 1–128 operations (identical for file and stdin), single JSON document (trailing whitespace allowed, trailing values rejected), UTF-8 only, BOM rejected, regular files only (directories/FIFOs rejected).

Key matching is exact and case-sensitive (`Op` ≠ `op`). Duplicate keys are rejected even when written with different escape sequences (comparison is on decoded key values).

## 5. JSON output schema (batch result v1)

The example below assumes the project starts with one open required `security` cell; the batch has two operations that add `security.csrf` and `tests` (same scenario as the README sample):

```json
{"batch_result_version":1,"dry_run":true,"changed":true,"operations":2,"required_gaps_before":1,"required_gaps_after":2,"changes":[{"id":"security","before":{"parent":"","status":"open","required":true},"after":{"parent":"","status":"expanded","required":true}},{"id":"security.csrf","before":null,"after":{"parent":"security","status":"open","required":true}},{"id":"tests","before":null,"after":{"parent":"","status":"open","required":true}}]}
```

Field order is fixed as above; output is compact one-line JSON plus exactly one LF. `changes` is always an array (empty `[]` for a semantic no-op). Added cells have `before:null`. Cells whose final state equals the original are omitted. Gap counts come from the existing `State.Counts()`. `batch_result_version` is an output schema version independent of the state schema and of the `status`/`gaps` output schemas, which remain unchanged. Apply mode uses the same schema with `dry_run:false`, emitted only after a successful save.

## 6. State transition semantics

Operations apply in array order; no implicit sorting. Parent-before-child ordering is the caller's responsibility (adding a child before its parent fails the same way the interactive `add` does). Marking the same cell multiple times is allowed; only the final status matters. `done` in batch input is expressed as `mark` with `status:"done"`. A batch whose net effect returns every cell to its original state is a semantic no-op: it reports `changed:false` and triggers no save. Domain transitions are performed exclusively by the existing `State.Add` and `State.Mark`, so batch and interactive behavior cannot diverge.

## 7. Atomicity boundary

Guarantee: within one CLI run, either every operation succeeds, the final state validates, and `Save` replaces `state.json` exactly once — or no operation is persisted and `state.json` is byte- and mtime-identical to before. Mechanism (Architecture A):

1. Validate flags; read bounded input; strict-parse.
2. Resolve project; `Load` original state.
3. Deep-copy the state (fresh `Cells` backing array; the working copy shares no mutable storage with the original).
4. Apply operations in order via existing mutators on the copy; wrap failures with the 1-based operation index, op kind, and ID while preserving the `*Problem` code via `%w`.
5. `Validate()` the final copy.
6. Compute the semantic diff and gap counts.
7. Dry-run: stop, output preview. Semantic no-op: output, skip save. Otherwise `Save(root, copy)` — the existing temp-file + fsync + rename writer — exactly once.

Not covered (documented in README): filesystem failure between rename steps, power loss, concurrent writers, stdout write failure after commit (retrying after a post-commit stdout failure is not automatically safe), crash durability.

## 8. Dry-run guarantees

`--dry-run` performs the same flag validation, bounded read, strict parse, project resolution, load, ordered apply, and final validation as an apply. It never calls `Save`, never writes any file under `.mandala` (no temp files), never touches Git-local exclude or `.gitignore`, and leaves the state schema untouched. Success exits 0 (including semantic no-op); validation failures exit 2 with empty stdout. A failure while writing the preview may leave partial output, but state remains unchanged. Dry-run validates changeability; it does not reserve or lock the state for a subsequent apply.

## 9. Failure matrix

| Failure | Stage | Code | Exit | State file | stdout |
|---|---|---|---|---|---|
| Missing/empty/duplicate `--file`, unknown flag, positional arg | flags | `E_USAGE` | 2 | untouched | empty |
| Unreadable file, non-regular input | input read | `E_IO` | 2 | untouched | empty |
| Input > 65,536 bytes | input read | `E_LIMIT` | 2 | untouched | empty |
| Malformed JSON, BOM, invalid UTF-8, duplicate/unknown/case-variant keys, null, bad types, wrong `batch_version`, trailing JSON | parse | `E_BATCH_INVALID` | 2 | untouched | empty |
| Operations count 0 or >128 | parse | `E_LIMIT` | 2 | untouched | empty |
| No project / missing state | project | `E_NO_PROJECT` | 2 | untouched | empty |
| Invalid ID, duplicate cell, missing parent, unknown cell, expanded mark, closed-parent add, forbidden transition | operation i | per existing mutator (`E_USAGE`, `E_DUPLICATE_ID`, `E_INVALID_PARENT`, `E_UNKNOWN_NODE`, `E_STATE_INVALID`) | 2 | untouched | empty |
| Final state invalid (limits) | validation | `E_LIMIT` / `E_STATE_INVALID` | 2 | untouched | empty |
| Save I/O failure | save | `E_IO` (default) | 2 | prior bytes preserved by existing writer | empty |
| stdout write error returned after successful save | output | `E_IO` | 2 | committed; not rolled back | may contain partial JSON |

Diagnostic format: `mandala: <CODE>: batch operation <n> (<op> <id>): <cause>` for operation-stage failures (e.g. `mandala: E_INVALID_PARENT: batch operation 2 (add security.csrf): missing parent "security"`). Invalid IDs are quoted and limited to a prefix of at most 64 bytes at a UTF-8 character boundary, in both the operation context and the cause. Existing `Problem` codes and short-ID diagnostics are preserved. Fixed checking order: flags → input read/size → JSON structure → project/state → ordered operations → final validation → save → output. Input, operation, validation, and save failures leave stdout empty. After a successful save, a stdout write failure does not roll back state and may leave partial JSON.

## 10. Module ownership

| Unit | Owns | Depends on |
|---|---|---|
| `batch_input.go` | bounded read (file/stdin), strict token-level JSON parse, operation typing, limits | model, `problem` |
| `batch.go` | operation model, deep copy, ordered apply via `Add`/`Mark`, final validation, semantic diff, and the CLI adapter (flags, duplicate `--file` detection, stdin injection, project resolution, load/save orchestration, exit mapping) | `State`, `Cell`, `ProjectRoot`, `Load`, `Save` |
| `batch_render.go` | deterministic JSON and text rendering of results | diff types |
| `command.go` | dispatch of `batch` (with `stdin` injection), command help registration | `executeBatch` |

No JSON parsing or file I/O inside the batch core; no rendering inside the core.

## 11. Data flow

```
argv ──> flag validation ──> bounded read (file|stdin) ──> strict JSON parse
      ──> ProjectRoot ──> Load ──> deep copy ──> ordered Add/Mark
      ──> Validate ──> diff(original, work) ──> ┬─ dry-run ──> preview ─┐
                                                ├─ no-op ────> result ──┤
                                                └─ else ──> Save once ──> result
                                                                          └─> stdout (buffered)
```

## 12. Alternatives considered

- **Architecture B (separate batch mutator): rejected.** Duplicates every domain rule (parent expansion, optional inheritance, rollback) now enforced inside `Add`/`Mark`; any future rule change would have to be made twice and could diverge. Chosen Architecture A reuses mutators on a deep copy, so interactive and batch behavior are identical by construction.
- **Separate state writer for batch: rejected.** `Save` already provides validate, sort, temp-file, fsync, rename; reusing it keeps one write path.
- **`json.Decoder.DisallowUnknownFields` alone: insufficient.** It cannot reject duplicate keys (last-wins silently), escaped-form duplicates, or enforce exact key sets per operation type. A token-level parser is required; `DisallowUnknownFields` is not used for batch input.
- **Diffing operation-by-operation: rejected.** Preview must reflect the final persisted state and collapse repeated marks on the same cell; a state-vs-state semantic diff does this naturally and stays deterministic under input reordering.
- **Extending `Run`'s public signature with stdin: rejected** (public API churn). `Run` wraps an internal `run` that carries an `io.Reader`; existing callers and the public signature are unchanged.

## 13. Compatibility invariants

- State schema stays v1; on-disk format unchanged (same marshal, sort, indent, trailing LF).
- Existing command contracts, help texts (except the root command list gaining `batch`), exit-code semantics, `status`/`gaps`/`show` JSON schemas unchanged.
- Single-writer model unchanged; offline; stdlib-only; `go.mod` untouched.
- Existing tags untouched; no history rewrites.

## 14. Testing strategy

Mandatory matrix from the specification:

- **T01 input parsing**: golden accepts (file, stdin) and rejects (missing/duplicate `--file`, missing file, directory input, empty input, 65,536-byte boundary accept vs 65,537 reject, 0/129 ops vs 128 ops, trailing JSON, duplicate keys incl. escaped forms, unknown fields, case variants, null, malformed JSON, invalid UTF-8, BOM, version mismatches incl. `1.0`/`1e0`/`"1"`, wrong `optional`/`status` types, per-op forbidden keys).
- **T02 semantics**: multi-add/multi-mark/add+mark, optional inheritance, parent expansion on child add, child-before-parent failure, in-batch duplicate add, mark of unknown/expanded cells, add under closed parent, repeated marks, round-trip semantic no-op, 8-root/8-child boundaries, 72-cell boundary, capacity overflow.
- **T03 atomicity**: for first/middle/last operation failures and parse/validation failures, state.json bytes and mtime unchanged and no temp files left; successful batch saves exactly once (byte-level observation of `.mandala` directory); semantic no-op does not save; save failure surfaces as error.
- **T04 dry-run**: correct content, byte/mtime/Git-metadata immutability, no temp files, deterministic stdout, exit codes, empty stdout on failure, dry-run then apply yields the same final diff.
- **T05 preview**: ID ordering, input-order independence, storage-order independence, `open→expanded` shown, added cells shown, marks shown, required/optional correctness, no-op empty changes, gap counts, fixed JSON field order, compact output, single trailing LF, exact text format, byte-identical repeated runs.
- **T06 CLI integration**: real binary (`go build`), `--project` present/absent, relative/absolute input paths, stdin, silent apply, `--json` apply, clean stderr, error stdout emptiness, exit 2, version/help compatibility, existing command behavior unchanged, Windows-compatible test code paths.
- **T07 existing contracts**: full existing suite green plus schema/exit/discovery/exclude/symlink/atomic-replace/clean-safety/no-network/no-deps checks.
- **Properties P1–P6** (batch ≡ sequential mutators; failed batch leaves state untouched; dry-run diff equals apply diff; preview order independent of storage order; no-op writes nothing; deterministic output with no OS-dependent values) as Go tests with repetition over shuffled storage orders and permuted-but-equivalent inputs.
- **Mutation checks** (validation-before-save removal, per-op save, deep-copy removal, changes sort removal, dry-run save, duplicate-key acceptance) are performed in a scratch clone, never on the working tree; they must make the suite fail.

Local gates: `go test -count=1 ./...`, `go test -shuffle=on -count=1 ./...`, `go test -race -shuffle=on -count=1 ./...`, `go vet ./...`, `go build ./...`, `git diff --check`. CI: existing 10 jobs retained; batch cases appended to the Ubuntu CLI smoke script (actionlint if CI files change).

Recorded exception (human review item): `TestBatchSaveFailure` skips on Windows because `os.Chmod` cannot make a directory unwritable there, so this directory-level real-I/O injection is not portable. A Windows-specific alternative may exist — making `state.json` read-only could make `Save`'s rename fail because the Go runtime does not pass `FILE_RENAME_IGNORE_READONLY_ATTRIBUTE` — but it is unverified on Windows (audit round 3, MINOR-4) and is left as a human decision: either add a Windows-specific injection branch or grant an explicit exemption. Compensating coverage runs on every platform (`TestBatchSaveErrorPropagation` verifies exit 2, empty stdout, the `E_IO` diagnostic, an untouched state, and no success JSON via seam injection); the real filesystem failure remains covered on Unix. Unverified scope: a genuine OS-level write failure inside `Save` on Windows. The same skip convention already exists in v0.4.1 (`status_json_command_test.go`).

## 15. Remaining risks

- Multi-process concurrency and lost updates (single-writer assumption; documented).
- Save I/O failure after temp-file creation leaves the old `state.json` in place (existing writer semantics; temp file removed).
- stdout failure after commit: the JSON result may be missing or partial though the batch was applied. A write error returned to the CLI reports `E_IO` with exit `2`, which does not prove that the batch was not applied. The saved state is not rolled back. Do not retry automatically; check the current state with `show --json` before deciding whether to retry. Exactly-once execution is not guaranteed. Re-running a batch is safe but not result-identical: repeating an `add` whose cell now exists fails atomically with `E_DUPLICATE_ID` (nothing applied), while re-running `mark`-only operations converges to a semantic no-op (`changed:false`, no save).
- Dry-run/apply race: state may change between the two; dry-run output is not a reservation.
- No enforcement that two agent processes serialize; future state-hash precondition would address this.

## 16. Acceptance criteria

1. All four features implemented behind `mandala batch` with the exact CLI/JSON/text contracts above.
2. Full local gates green on Linux/macOS dev box (the CI matrix runs remotely): tests, shuffle, race, vet, build, `git diff --check`.
3. Mandatory test matrix T01–T07 and properties P1–P6 present and passing.
4. No regression in existing commands or output schemas.
5. README documents batch usage, atomicity scope, dry-run caveats, and single-writer limits; release-notes draft produced.
6. Independent audit (Claude) returns zero BLOCKER and zero MAJOR findings.
7. Nothing committed, pushed, tagged, or released without explicit human approval.
